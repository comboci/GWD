## مشکل اثبات‌شده در سورس

تابع `RunSourceTests` روی Thread رابط کاربری WinForms، `Application.DoEvents()` را فراخوانی می‌کرد و سپس چندین پیمایش recursive فایل، تشخیص ASP.NET Core/.NET/Node و اعتبارسنجی فرانت‌اند را به‌صورت همگام اجرا می‌کرد. `DoEvents` اجازهٔ reentrancy رویدادهای جدید وسط اعتبارسنجی را می‌دهد؛ پیمایش فولدرهای بزرگ می‌تواند UI را تا پایان اسکن مسدود کند. این تحلیل از ترتیب کد اثبات می‌شود، نه اندازه‌گیری تأخیر واقعی.

## اصلاح محدود

1. `RunSourceTests` اکنون **درخواست Preflight** می‌سازد؛ پس از debounce دویست میلی‌ثانیه‌ای، `InspectSourcePreflight` توسط `Task.Run` به Threadpool منتقل می‌شود. هیچ کنترل WinForms یا دادهٔ متغیر `_profile` داخل worker خوانده یا نوشته نمی‌شود.
2. هر درخواست `CancellationTokenSource` و شمارهٔ generation اختصاصی دارد. تغییر سورس، حالت Build یا مسیر Prepared، درخواست قدیمی را لغو می‌کند. با Dispose شدن کنترل نتیجه (خروج از صفحه) نیز لغو انجام می‌شود.
3. فقط در صورت زنده بودن صفحه، همخوانی source/mode/prepared-path با درخواست و جدیدبودن generation، نتایج PASS/FAIL در UI نمایش داده می‌شوند. نتیجهٔ قدیمی روی ورودی جدید نوشته نخواهد شد.
4. `Application.DoEvents()` حذف شد. اولین Preflight صفحه پس از `Shown` شروع می‌شود تا Message Pump آماده باشد. پیام‌های PASS/FAIL و کنترل‌های قبلی `RefreshPreparedPublishValidation` حفظ شده‌اند. خطاها ثبت و بدون Crash شدن UI نمایش داده می‌شوند.
5. رفتار اسکن محیط، Deployment، IIS/SQL، Backup و Rollback دست‌نخورده باقی ماند.

## محدودیت و موارد بعدی

- `Detect()` هنگام تغییر Source و `UpdateNavigationState()` همچنان با `DetectApiProject` اسکن همگام انجام می‌دهند؛ **این اصلاح فقط Source Preflight را از Thread UI جدا کرده و حذف تمام نقاط کندی ادعا نمی‌شود**. مورد جداگانهٔ UI برای cache/debounce تشخیص اولیه و اعتبارسنجی Next لازم است.
- `DetectApiProject` و `DetectNodeRequirement` خودشان cancellation token ندارند؛ اگر سیستم‌فایل کند باشد، worker ممکن است تا برگشت API به اجرای داخلی ادامه دهد، اما نتیجهٔ لغوشده در UI اعمال نمی‌شود.
