# GWD V262-R — اصلاح خواندن لاگ فعال و حفاظت از خطای اصلی Deploy

## ورودی Runtime Review کاربر

- محصول نمایش‌داده‌شده: Generic Web Deployment Manager V261، مرحله Review and Deploy (8/8)
- خطا: `The process cannot access the file 'C:\ProgramData\NSP\DeploymentManager\Logs\Deploy-20261123-115100-3841.log' because it is being used by another process.`
- لاگ قابل مشاهده: `DEPLOYMENT UNSUCCESSFUL`، `ROLLBACK SKIPPED`، `COMMIT SKIPPED`؛ وضعیت بازیابی نیازمند بررسی مستقل است.
- این خطا می‌تواند هنگام تلاش برای استخراج tail لاگِ **در حال نوشتن** توسط بخش تولید گزارش رخ دهد و علت **اولیه** Deploy را مخفی کند. تا زمان دریافت محتوای گزارش اصلی، خود علت اولیه مشخص نیست.

## شواهد سورس در HEAD V261

- `LogService.OpenWriter` فایل جلسۀ فعال را با `FileAccess.Write` و `FileShare.Read` باز نگه می‌دارد.
- `WizardForm.ReadRecentLogLines` از `File.ReadLines(path)` استفاده می‌کرد. Share-mode پیش‌فرضِ این خواننده اجازه نمی‌دهد فایل با handle نوشتۀ باز مشترک شود؛ در ویندوز، Sharing Violation رخ می‌دهد.
- `DeployAsync` در بلوک catch به‌صورت بدون محافظ `CreateErrorReport(ex)` را صدا می‌زد و خطای گزارش تشخیصی ممکن بود به بیرون پرتاب شود و پیام اصلی استقرار را جایگزین کند.
- هیچ تغییری در مالکیت IIS attempt، backup، rollback، و مراحل BUILD/HEALTH/COMMIT وجود ندارد.

## اصلاحات سورس V262

1. `DeploymentLogTailReader.ReadLastLines` از `FileStream(FileAccess.Read, FileShare.ReadWrite | FileShare.Delete)` به‌همراه `StreamReader` استفاده می‌کند. خواندن هم‌زمان writer با حد حافظۀ آخرین `maxLines` ممکن می‌ماند و هیچ writer یا log session بسته نمی‌شود.
2. اگر فایل به‌طور انحصاری توسط یک فرآیند بیرونی قفل یا مجوز خواندن رد شده باشد، خطا به شکل **هشدار مستقل در گزارش** ثبت می‌شود، نه به جای استثنای اصلی.
3. شکست `CreateErrorReport` در `DeployAsync` به‌طور مستقل ثبت می‌شود؛ پنجرۀ خطا همیشه استثنای اصلی را نشان می‌دهد، حتی اگر فایل گزارش قابل ساخت نباشد.
4. عنوان فایل diagnostic به جای V32 ثابت، از `ProductInfo.DisplayVersion` خوانده می‌شود.
5. تست رگرسیون در `tests/IisSafety.Tests` اضافه شد: نگه داشتن writer با `FileShare.Read` و خواندن tail در همان زمان، نوشتن خط جدید در حضور reader، خواندن tail محدود و نبود فایل.

## موارد عمدیِ بدون تغییر

- عدم تغییر `LogService.OpenWriter` یا محدودیت writerهای متعدد؛ مکانیزم append همچنان دقیقاً یک owner دارد.
- عدم تغییر IIS، database، cache، backups، recovery markers، SQL credentials و deployment state.
- هیچ repair خودکاری برای وضعیت `RECOVERY REVIEW REQUIRED` انجام نشده است.

## وضعیت تأیید

- `SOURCE_CORRECTION=PREPARED`
- `BUILD=NOT_RUN`
- `AUTOMATED_TESTS=NOT_RUN`
- `RUNTIME_REVIEW=PENDING_USER`
- `IIS_DEPLOY=NOT_RUN`
- مسئول Build، Test و Runtime Review: کاربر.

## گام‌های Runtime Review کاربر

1. با برنامه V262، شکست کنترل‌شده در مرحله Build یا preflight ایجاد کن؛ در حالی که writer فعال است، گزارش Diagnostic باید تولید شود و استثنای اصلی در پنجره حفظ بماند.
2. همان فایل لاگ فعال را هم‌زمان در Log Viewer باز کن و در وضعیت append، Refresh کن؛ پیام‌ها باید بدون Sharing Violation خوانده شوند.
3. اگر فایل Log را فرایند بیرونی exclusive باز کند، گزارش اصلی نباید با خطای Log جایگزین شود.
4. قبل از Deploy واقعی به IIS، وضعیت recovery markers، IIS app pool/site و backupها را بررسی کن. خطای این تصویر اثبات سلامت بازیابی نیست.
