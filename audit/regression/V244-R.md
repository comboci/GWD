## نقص اثبات‌شدهٔ جدید — P1 (مخدوش‌شدن وضعیت Recovery Journal)

در `Program.RollbackAsync` پس از `StopSiteForDeploymentAsync` (که `MutationStarted` را ثبت می‌کند)، `Directory.Move(profile.HostingRoot, failed)` و سپس `CopyTree` بدون `_iisAttempt.FilesChanged=true` انجام می‌شد. این پرچم در مسیر `ActivateStagingAsync` ست می‌شود، اما Rollback CLI این مسیر را صدا نمی‌زند. در Crash بعد از اولین جابه‌جایی، Journal می‌توانست `FilesChanged=false` داشته باشد، هرچند فایل‌های میزبانی تغییر کرده‌اند. `*.unresolved` همچنان محافظت می‌کند، پس عدم انسداد Deploy جدید اثبات نشده؛ مشکل، شواهد نادرست برای بررسی دستی است.

## اصلاح محدود V244-R

1. API `DeploymentService.RecordExternallyManagedFileMutation()` تنها در حضور تلاش IIS فعال و حل‌نشده، با `MutationStarted=true`، در Journal `FilesChanged=true` را با Save/Flush موجود ثبت می‌کند؛ در شکست ذخیره‌سازی اجازهٔ ورود به تغییر فایل نمی‌دهد.
2. CLI در `RollbackAsync` بلافاصله پس از بررسی مجدد Backup و پیش از هر `Directory.Move` یا `CopyTree` این API را صدا می‌زند.
3. **پرچم داخلی `DeploymentService._filesChanged` عمداً دست‌نخورده می‌ماند**؛ این پرچم مسیر جبرانی مخصوص ActivateStaging را کنترل می‌کند و تغییر آن، در شکست پیش از swap، می‌تواند مسیر بازگرداندن IIS در CLI را مختل کند. جبران CLI جداگانه باقی می‌ماند.
4. هیچ backup، marker، journal تاریخی، یا تنظیم IIS به‌طور خودکار پاک نمی‌شود. نسخه `243.0.0` به `244.0.0` افزایش یافت.

## شکاف‌های باقیمانده

- **A03=IN_PROGRESS:** مسیر CLI Rollback پس از `HealthCheckAsync`، فقط سلامت HTTP عمومی را چک می‌کند؛ یک بازبینی جداگانه برای هویت نسخهٔ زنده API/frontend لازم است تا restore پاسخ‌گوی نسخهٔ مورد انتظار باشد.
