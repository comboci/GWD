## یافتهٔ واقعی و منطق ایمنی

در `DeploymentService.PublishAsync`، چهار شرط حفاظتی `if (false && profile.BuildMode == "Fast IIS Update" ...)` در نسخه مبنا حوالی خطوط **415، 531، 551 و 773** باعث شده‌اند مسیرهای کپی Hosted Baseline، رد کردن frontend build و reuse وب‌روت غیرفعال بمانند. `fastPreviousState` و `fastCurrentState` مقدار اولیه null دارند و به‌دلیل غیرفعال‌بودن شرط اصلی تغییر نمی‌کنند. بنابراین در عمل اجرای Fast IIS Update همچنان npm build در صورت نیاز، `dotnet publish` و مسیر فعال‌سازی IIS را انجام می‌دهد؛ فقط کنترل‌های سریع‌تر dependency/cache ممکن‌اند.

بااین‌حال UI در Source، Target و Review به‌صراحت ادعا می‌کرد `Fast IIS Update` از باینری‌های Hosted استفاده می‌کند و مراحل بی‌تغییر را Skip می‌کند. این **نقص مستند و قابل‌اثبات** موجب انتخاب Mode با انتظار غیرواقعی از سرعت و استفادهٔ مجدد نسخهٔ مستقرشده می‌شد.

## چرا فعال‌کردن چهار شرط در این مرحله مجاز نیست

1. `ReadSmartState(profile)` یک وضعیت persist شده را از Repository یا Hosted folder می‌خواند؛ انطباق آن با Snapshot واقعی IIS physicalPath، Owner/Release-ID کنونی، صحت کامل wwwroot و API فعال، و مالکیت rollback **پیش از** کپی Hosted Baseline در شاخهٔ غیرفعال‌شده اثبات نمی‌شود.
2. در حالت تغییر صرفاً frontend، شاخهٔ Hosted Baseline قادر است قبل از مسیر full-build با `return output` برگردد؛ درحالی‌که تولید `gwd-frontend-release.json` و `gwd-release-integrity.json` جدید و اعتبارسنجی source/backend identity در مسیر full-build بعد از آن انجام می‌شود. باید اثبات شود که reuse هیچ‌وقت manifest کهنه یا نامعتبر ایجاد نمی‌کند.
3. `ComputeSmartState` MigrationHash را جداگانه و با یک فهرست مشخص از مسیر/نام فایل‌ها حساب می‌کند. برای اعتماد به Skip هنگام تغییر DB/initializer یا تنظیمات، پوشش fingerprint و contract اجرای migration باید مستقل ممیزی شوند.
4. جایگزینی شرط `false` با `true` یا حذف آن بدون سناریوهای Runtime/Failure Injection و اثبات Backup/Journal/Restore، خطر استفاده از نسخهٔ اشتباه یا Rollback تأییدنشده دارد؛ بنابراین **در V255 هیچ‌یک از مسیرهای Fast Skip فعال نشدند**.

## اصلاح محدود این نسخه

- `WizardForm`: سه متن UI مربوط به Fast IIS Update در صفحهٔ Source، Target و Review اکنون صریحاً می‌گویند مسیر فعلی fresh frontend build (در صورت نیاز) و `dotnet publish` است و shortcuts مبتنی بر hosted baseline/fingerprint غیرفعال‌اند.
- `DeploymentService.PublishAsync`: پس از اعلام BuildMode، یک پیام `[FAST][SAFETY]` در Session Log اضافه شد تا هنگام اجرا نیز وضعیت واقعی روشن باشد. توضیح قدیمی و گمراه‌کنندهٔ کنار بلوک Fast اصلاح شد.
- **هیچ تغییری** در شرط‌های حفاظتی `if(false &&)`، محاسبات SHA256/Fingerprint، مراحل npm/dotnet، SQL، IIS، Backup، Recovery، Markerها، Publish/Health Verification یا مدیریت فایل‌ها انجام نشد.

## وظایف پیشنهادی قبل از فعال‌سازی واقعی Fast IIS (اولویت آینده)

- `UI10-F1`: بستن provenance به site/app/pool/physicalPath و Release-ID نسخهٔ فعال، همراه با hash دقیق Hosted payload؛ هر دادهٔ ناقص → Full Build.
- `UI10-F2`: انتشار یک release manifest و frontend/API markers تازه و معتبر حتی با استفادهٔ مجدد از باینری، اثبات Version Contract و صحت hash Staging/Activated/HTTP.
- `UI10-F3`: پوشش جامع DB Migrations/DbInitializer/config، hash ورودی‌های وابستگی و تغییر فایل‌های خارج از فهرست؛ تغییر یا ابهام → Full Publish.
- `UI10-F4`: بررسی rollback ownership، journal، BackupIntegrity، محافظت در برابر فایل تغییر‌یافته حین کپی و fail-closed هنگام mismatch.
- `UI10-F5`: تست‌های پذیرش توسط کاربر/محیط ایزوله: no-change، frontend-only، backend-only، migration-only، دستکاری Hosted، manifest corrupt/missing، startup failed، HTTP stale، interrupted deployment و failure injection. تا قبل از آن optimization نباید فعال شود.
