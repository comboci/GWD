## نقص تأییدشده در سورس — P1: تخریب شواهد قبلی هنگام preflight شکست‌خورده

در `IisDeploymentAttempt` نسخه V241، سازنده پس از گرفتن exclusive lock، روی هر `*.lock` فوراً `SetLength(0)` و `Write(owner=new-attempt)` می‌زد و **بعداً** وجود `*.unresolved` تلاش قبلی را بررسی می‌کرد. بنابراین صرف تلاش دوباره پس از Crash می‌توانست متن مالک/Journal تلاش قبلی را از Lockها پاک کند، حتی اگر تلاش جدید در preflight بلاک شود. بررسی با `File.Exists` نیز در برخی حالت‌های عدم دسترسی ممکن است غیاب فایل را به‌اشتباه گزارش کند.

## اصلاح محدود

1. تمام leaseهای موجود ابتدا با `FileShare.None` صرفاً **باز می‌شوند**؛ محتوا هنوز پاک/بازنویسی نمی‌شود.
2. Markerهای مستقیم پس از کسب همهٔ leaseها با `File.GetAttributes` بررسی می‌شوند. فقط `FileNotFoundException` نشانهٔ غیاب پذیرفته می‌شود؛ دسترسی‌نداشتن، Directory Missing، link/reparse یا پوشه‌ای بودن Marker باعث توقف fail-closed است.
3. اگر Marker موجود باشد، تابع `DescribeUnresolvedMarker` با دامنهٔ محدود، فقط **برای تشخیص** Attempt ID امن، محل Journal مربوطه و سه فلگ `Resolved/MutationStarted/FilesChanged` را نمایش می‌دهد؛ عدم خواندن، ناسازگاری ID، پیوند بودن Journal، JSON معیوب و فایل غیرمتعارف همگی `UNVERIFIED` هستند. هیچ مقدار Journal مجوز پاک‌سازی/ادامهٔ استقرار نیست.
4. شواهد مالکیت Lock جدید فقط بعد از عبور از همهٔ بررسی‌های Marker و ancestor/nested نوشته و flush می‌شود. اگر Marker موجود باشد، محتوای Lock قبلی برای بررسی باقی می‌ماند.
5. مسیرهای واقعی IIS، rollback، backup، `Resolve` و حفاظت V241 در برابر حذف زودهنگام Backup تغییر نکرده‌اند.
6. نسخه: `241.0.0 → 242.0.0`.

## سناریوها و محدودهٔ ادعا

- Crash بعد از شروع mutation و قبل از Resolve: Marker تلاش قبلی باقی می‌ماند؛ تلاش بعدی باید بدون تخریب Lock قبلی بلاک و Journal را فقط read-only توصیف کند.
- Journal دارای `Resolved=true` با Marker باقی‌مانده: همچنان بلاک می‌شود؛ Resolved بودن به معنی اجازهٔ پاک‌سازی خودکار یا اثبات سلامت HTTP نیست.
- Marker نامعتبر یا unreadable و Journal missing/corrupt: fail-closed و ارجاع به بررسی دستی، بدون حدس دربارهٔ وضعیت.
- Markerهای nested/ancestor قدیمی هنوز مسیر حفاظتی مجزا دارند؛ شناسایی غنی تمام آن‌ها خارج از دامنهٔ این اصلاح است.
- بررسی مستقیم فایل‌ها ممکن است با TOCTOU و فعالیت نرم‌افزارهای non-cooperating مواجه شود؛ رفع آن نیازمند آزمون روی NTFS و تحلیل handle-based است.
- **Crash و قطع برق روی IIS واقعی آزمایش نشده‌اند**؛ توان Flush فایل به‌تنهایی تضمین power-loss durability تمام metadata نیست.
