## نقص قطعی

در شاخهٔ فعلاً غیرفعالِ Fast IIS Update، `RequireHostedBaselineProvenanceAsync` وضعیت IIS، Manifest، API/Frontend hash و HTTP را **پیش از** `CopyDirectory(profile.HostingRoot, output)` بررسی می‌کرد. در فاصلهٔ این دو، نویسندهٔ خارجی می‌تواند فایل‌های Hosted را عوض کند. نسخهٔ فعلی، قبل/بعد Copy، Inventory کامل و ثابتی از مبدأ و Staging را مقایسه نمی‌کرد؛ همچنین `ReissueReusedReleaseEvidence` می‌توانست محتوای API مرحلهٔ Staging را صرفاً بر اساس Hash همان مرحله دوباره seal کند. `IisDeploymentAttempt` قفل‌های مشترک میان فرآیندهای هماهنگ GWD را حفظ می‌کند ولی نویسندهٔ مستقل IIS یا برنامه را به‌طور عمومی قفل نمی‌کند.

## اصلاح منحصراً در مسیر dormant

1. `RequireFastHostedReusePreMutationLease`: فقط IIS Attempt قفل‌شده، زنده، unresolved و بدون mutation/file-change را می‌پذیرد و `AssertOwnership` را فراخوانی می‌کند. فقط `Local Server / Single Folder` با **CreateBackupBeforeDeployment و KeepPreviousDeploymentForRollback روشن** واجد مسیر reuse است. وجود وضعیت `_activeRollbackFolder` یا `_activeDisplacedFolder` و مالکیت سابق موجب رد می‌شود. این گزینه‌ها **تضمین وجود Backup نیستند**؛ در مسیر عادی Activation باید Backup کامل، manifest به‌نام همان attempt و SHA256 مطابق همچنان مستقل تهیه و تأیید شود.
2. `Hosted baseline SHA256 inventory`: تنها پس از تصمیم واقعی Reuse، **پیش از بازتأیید مجدد F1 در همان شاخه** و با `CaptureRecoveryInventory` موجود از همهٔ فایل‌ها و دایرکتوری‌های Hosted (نام نسبی و SHA256) در حافظه snapshot گرفته می‌شود. کنترل اولیهٔ F1 برای تمام حالات PreviousState همچنان برقرار است؛ Backend/Migration change می‌تواند بدون اجبارِ Backup policy مختص Reuse به Full Publish برود. Markerها و Backupها ایجاد/حذف/دست‌کاری نمی‌شوند.
3. `Hosted baseline pre-copy recheck`: درست قبل از `CopyDirectory` از `VerifyRecoveryInventory(host, snapshot)` استفاده می‌شود. هر تغییر مبدأ/فایل گم‌شده/اضافی باعث شکست Fail-Closed و باقی ماندن Staging ناقص می‌شود.
4. `Hosted staged snapshot compare`: پس از Copy، هم source مجدداً Hash می‌شود، هم محتویات Staging با **همان snapshot اولیه** مقایسه می‌شود. تنها فایل اختصاصی `F:.deployment-incomplete` در Staging از مقایسهٔ Payload کنار می‌رود و باید **وجود داشته باشد**؛ خود Marker حفظ می‌شود. سایر فایل/دایرکتوری‌های اضافی یا تغییر‌یافته ممنوع است. مقایسهٔ مسیرها/لینک‌ها با `RequireSeparate/RequirePlainTree` و `CaptureRecoveryInventory` انجام می‌شود.
5. پس از Copy، F1 (هویت Site/AppPool/HTTP release، Manifest و Source hash) و اجارهٔ IIS دوباره بررسی می‌شوند. پس از overlay فرانت‌اند و F2 Reissue، `HashPublishedApiPayload(output)` باید با هش API مبدأ **قبل از Copy** منطبق باشد؛ مبدأ دوباره بر اساس snapshot کنترل و F1 و Lease بازخوانی می‌شوند. بنابراین تغییر در طول Copy یا ساخت Staging موجب رد مسیر reuse می‌شود.
6. **چهار شرط `if(false && Fast IIS Update)` همچنان بدون تغییر حفظ شده‌اند.** مسیرهای CLI/Wizard فعال، IIS STOP، Backup/Restore، Journal/Recovery، SQL و نسخهٔ واقعی فایل‌های Hosted **تغییر داده نشده‌اند**. هیچ عملیات فایل/استقرار واقعی اجرا نشده است.

## محدودیت امنیتی و آزمون پذیرش

- Snapshot SHA256 دوطرفه **اتمیک نیست**: نویسندهٔ مستقل ممکن است بلافاصله پس از آخرین بررسی و پیش از Activation فایل‌ها را تغییر دهد؛ قفل GWD فقط فرآیندهای هماهنگ را serialise می‌کند. این مسئله هنوز به مکانیسم Snapshot فایل‌سیستمی/قفل نویسنده و تست‌های Failure Injection نیاز دارد؛ **Fast Skip با این نسخه قابل فعال‌سازی نیست**.
- `Backup/Recovery` در Active Deployment همچنان منطق خودش را اجرا می‌کند. فعال بودن CheckBox Backup معادل سلامت backup واقعی نیست. هیچ `.unresolved` یا `.complete.json` در این اصلاح پاک نمی‌شود.
- شاخهٔ غیرفعال دوم `Reuse hosted wwwroot` در مسیر Full-Publish همچنان نیازمند ممیزی مستقل لایهٔ Snapshot/Release Contract قبل از فعال‌سازی است؛ هیچ مسیر Reuse فعال نشده است.
