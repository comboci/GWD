## اصلاح محدود F2

1. `HashPublishedApiPayload`: مجموعهٔ فایل‌های DLL/EXE/DEPS.JSON/RUNTIMECONFIG.JSON و کتابخانه‌های اجرایی native در خروجی منتشرشده (شامل زیرپوشه‌ها؛ بدون `wwwroot` و تنظیمات متغیر دیتابیس) را با SHA256 و نام نسبی فایل‌ها هش می‌کند. اگر باینری اصلی، مسیر امن یا فایل مورد انتظار موجود نباشد، **Fail-Closed** است. این هش فقط **تمامیت فایل‌های منتشرشده روی دیسک** را اثبات می‌کند؛ نه اصالت رمزنگاری‌شدهٔ نویسنده و نه باینری در حال اجرای پردازش IIS.
2. Manifest جدید در مسیر عادی Fresh Publish اکنون یک فیلد افزودهٔ `apiPayloadSha256` دارد. `VerifyActivatedDeployment` اگر فیلد وجود داشته باشد باید هش واقعی باینری‌های منتشرشده را با آن مقایسه کند؛ ناسازگاری باعث شکست صحت Deployment می‌شود. Manifestهای قدیمی با فیلد غایب قابل‌خواندن باقی می‌مانند اما «API payload UNVERIFIED» در Log ثبت می‌شود و اجازهٔ Fast Reuse نمی‌گیرند.
3. F1ِ غیرفعال توسعه یافت: Manifest باید `apiPayloadSha256` معتبر و مطابق فایل‌های Hosted داشته باشد؛ همچنین `frontendBuildSha256` Marker باید با هش Frontend بدون خود Marker برابر باشد. نبود/خرابی هر شاهد موجب `FAST_BASELINE_UNVERIFIED` پیش از copy می‌شود.
4. `ReissueReusedReleaseEvidence` فقط در **شاخهٔ `if(false && ...)`** و پس از کپی Hosted Baseline و Frontend Overlay به Staging جدید متصل شد: Marker قدیمی فقط در Staging حذف می‌شود، UI Version Contract دوباره بررسی می‌گردد، یک `releaseId` تازه و Marker `gwd-frontend-release.json` جدید ساخته و سپس Manifest تازه شامل `frontendSha256`، `apiPayloadSha256`، source/API/frontend path و version evidence صادر می‌شود. هش‌های Staging قبل از بازگشت دوباره کنترل می‌شوند؛ Hosted source هرگز دست‌کاری نمی‌شود.
5. `WriteSmartState` بعد از انتشار شواهد جدیدِ Staging اجرا می‌شود تا `FrontendOutputHash` با نسخهٔ جدید Marker منطبق باشد.
6. **چهار شرط `false && Fast IIS Update` همچنان حفظ شده‌اند.** مسیرهای IIS/SQL/Backup/Recovery/rollback و سیاست انتشار بدون تغییر مانده‌اند؛ هیچ‌کدام از Shortcutهای Fast فعال نشده است.
